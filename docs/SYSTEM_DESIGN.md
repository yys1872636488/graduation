# 《集成机器视觉的服装产品数字化追溯管理系统设计与实现》开发设计总纲

> **文档用途**：作为毕业设计的长期设计记录和 Claude Code 的项目开发上下文。后续开发应以本文为准；如果代码现状与本文冲突，先检查现有实现和数据库迁移，再提出差异，不要擅自大规模重构。
>
> **项目定位**：面向服装企业的内部业务管理系统，以原材料批次为起点，串联采购、来料质检、生产、成品质检、仓储、销售、售后，支持按批次正向/反向追溯。机器视觉仅用于“布料来料检验”的图片辅助检测，不做工业相机实时采集，不要求训练复杂模型。

---

## 1. 项目目标与边界

### 1.1 要解决的问题

服装产品在采购原材料、检验布料、生产加工、成品质检、仓储、销售和售后过程中会产生分散的数据。系统需要将这些数据通过订单、原材料批次、生产工单、成品批次、发货记录等关联起来，形成完整的产品生命周期追溯链。

系统应实现：

1. 管理用户、角色、权限和基础档案。
2. 管理供应商、原材料、服装产品和 SKU。
3. 管理采购订单、到货登记、原材料批次。
4. 上传布料图片，调用 YOLO 检测接口识别可能的布料瑕疵，并由人员复核后形成正式质检结论。
5. 管理生产计划、工单、领料批次、生产进度、成品质检及不合格品处理。
6. 管理原材料和成品库存，记录所有出入库流水。
7. 管理销售订单、发货、退换货和售后记录。
8. 支持从原材料批次追到生产工单、成品批次、销售和售后，也支持从成品或售后记录反向追溯原料来源。
9. 提供必要的工作台、条件查询、状态展示和简单统计。

### 1.2 明确不做的事情

为控制本科毕设工作量，第一版不实现以下内容：

- 不接入工业相机，不做生产线实时视频检测。
- 不自行训练大型或复杂的 AI 模型。
- 不做复杂的 APS 智能排产算法，不做 ERP/MES 等外部系统对接。
- 不做消费者个人衣柜或面向消费者的电商平台。
- 不要求追踪每一件衣服的单件级 RFID/二维码；以业务批次为主。
- 不要求多模态大模型、图文向量检索或复杂 AI 报告生成。
- 不把机器检测结果直接当成最终质量结论。
- 不允许绕过质检流程，把未放行的原材料或未通过成品质检的产品直接变成可用/可售库存。

如果现有开发时间不足，优先保证核心业务链和追溯链完整，统计图表及非核心交互可以简化。

## 2. 技术方案与项目结构

### 2.1 建议技术栈

- **前端**：Vue 3、Vite、Vue Router、Pinia、Element Plus、Axios。
- **业务后端**：Java + Spring Boot、Spring Security（或项目已有的等价认证授权方案）、MyBatis-Plus（或项目已有 ORM）。
- **数据库**：MySQL。
- **机器视觉服务**：Python + FastAPI（也可用 Flask，但整个项目只选一种），调用 YOLO 模型推理。
- **图片存储**：开发阶段可先保存到后端本地文件目录；数据库只保存相对路径/访问路径和元数据。若部署环境需要，再替换成对象存储。
- **接口文档**：Springdoc/OpenAPI 或项目已采用的接口文档方案。
- **版本管理**：Git；每完成一个可运行模块就提交一次。

### 2.3 前后端职责

- **前端**：页面展示、表单校验、筛选、分页、上传图片、显示检测图和业务状态。
- **Spring Boot 后端**：业务规则、权限验证、状态流转、数据关联、库存事务、审计日志、调用 Python 检测服务。
- **Python YOLO 服务**：接收图片并执行模型推理，返回结构化检测结果。它不直接修改采购订单、库存或最终质检结论。
- **MySQL**：保存业务数据、检测结果、质检结论、库存余额与库存流水、追溯关联关系。
- **文件存储**：保存原图和标注图；数据库保存文件地址、文件类型、大小、上传人和关联记录。

## 3. 用户角色与权限设计

系统采用 **一个统一后台界面 + 基于角色的菜单和操作权限**，不开发四套独立前端。用户登录后，根据角色显示允许访问的菜单和按钮。前端隐藏按钮只是体验优化，后端必须再次校验权限。

### 3.1 四类角色

#### A. 系统管理员

主要职责：维护账号、角色、权限、基础配置和系统运行记录。

可操作：
- 用户账号新增、编辑、禁用、重置密码。
- 角色和权限配置。
- 供应商、原材料、产品、SKU 等基础档案维护（如希望职责更清晰，也可仅授权基础数据维护）。
- 查看操作日志。
- 查看全局生命周期追溯与系统统计。

默认不允许：
- 随意修改已经确认的质检结论。
- 无记录地修改库存余额。
- 绕过业务流程直接把不合格批次改为合格。
- 删除已经被采购、生产、销售记录引用的关键业务数据。

#### B. 采购人员

主要职责：采购、到货和原材料批次登记。

可操作：
- 查看/维护供应商和原材料档案（权限由系统配置）。
- 创建、编辑、提交采购订单。
- 登记到货数量、到货日期、供应商批次信息。
- 建立原材料批次并查看批次详情。
- 查看来料检测结果、质检结论和原材料追溯。

默认不允许：
- 直接把原材料批次检验结论改成合格。
- 直接操作库存余额或伪造入库流水。
- 修改机器视觉模型结果。

#### C. 生产与质检人员

主要职责：生产执行、来料检验、成品质检和质量异常处理。

可操作：
- 查看生产计划、创建/执行工单（按授权范围）。
- 登记领料申请/领料明细，关联原材料批次。
- 登记生产进度。
- 对已登记的原材料批次上传布料图片，发起机器视觉检测。
- 复核检测结果并填写正式来料质检结论。
- 登记成品质检结果。
- 对不合格品执行返工、复检或报废处理。
- 查询库存、原材料和成品追溯。

默认不允许：
- 直接修改库存余额。
- 将未通过质检的原材料用于正常生产。
- 将未通过成品质检的产品转为可售库存。
- 修改已经产生的库存流水。

#### D. 仓储与销售人员

主要职责：仓库出入库、销售发货和售后处理。

可操作：
- 查询原材料/成品库存。
- 执行符合业务条件的原材料入库、领料出库、成品入库、销售出库。
- 查询库存流水。
- 创建和处理销售订单。
- 创建发货单，并选择允许发货的成品批次。
- 登记退换货、售后处理和验收结果。
- 查询成品批次追溯。

默认不允许：
- 将待检或不合格原材料入库为可用库存。
- 将未通过成品质检的产品作为可售成品入库。
- 将退回产品未经验收直接恢复成可售库存。
- 删除库存流水或历史发货记录。

### 3.2 权限实现原则

建议至少区分三类权限：

1. **菜单权限**：能否看到某个模块。
2. **操作权限**：能否新增、编辑、提交、复核、入库、出库、发货、报废等。
3. **数据权限**：第一版可简化为全局数据或按创建人/业务范围限制；若开发时间紧，不必做复杂组织树，但要在设计中说明。

后端接口应使用统一权限标识，例如 `purchase:read`、`purchase:create`、`inspection:review`、`inventory:inbound`、`shipment:create`。不要仅依赖前端路由守卫。

## 4. 页面总体布局与交互规则

### 4.1 统一布局

登录后进入统一后台框架：

- **左侧**：系统名称、动态菜单、菜单分组。
- **顶部**：面包屑、当前页面标题、当前用户、角色信息、修改密码、退出登录。
- **主内容区**：页面标题、简要说明、操作按钮、筛选区、表格/卡片、分页。
- **详情页**：基本信息 + 状态标签 + 关联记录 + 操作历史/追溯入口。

界面风格使用 Element Plus 常见后台样式，优先保证清楚、稳定、可用，不追求复杂动效。

### 4.2 通用页面规范

- 列表页一般包括：关键词/编号筛选、状态筛选、查询、重置、新增按钮、表格、分页。
- 表单页应有必填标识、格式校验、保存/取消按钮。
- 状态使用统一标签组件，颜色与含义全系统一致。
- 删除前确认；被其他业务记录引用的数据应禁止物理删除，改用停用/作废。
- 关键动作必须二次确认，例如提交订单、质检复核、库存出入库、报废、发货。
- 成功/失败必须提示，不允许按钮点击后无反馈。
- 表格中应显示业务编号、关键关联编号、状态、创建时间和操作入口。
- 重要详情页提供“查看关联记录”或“进入追溯”按钮。
- 先完成可运行的基本页面，不要先做复杂图表或装饰性功能。

## 5. 六大业务模块设计

## 模块一：系统管理与基础档案

### 5.1 系统管理

页面：
- 用户管理：用户列表、搜索、创建、编辑、禁用、重置密码。
- 角色管理：角色列表、角色编码、角色名称、说明。
- 权限配置：为角色分配菜单和操作权限。
- 操作日志：查询用户、操作类型、业务对象、操作时间、结果、必要的摘要。

规则：
- 密码必须安全存储，不能明文保存。
- 禁用用户后不可登录。
- 操作日志记录关键业务操作：订单提交、质检复核、库存变更、成品放行、发货、售后处置等。
- 管理员可以查询日志，但不能通过日志页面随意篡改业务历史。

### 5.2 基础档案

包括：
- 供应商：编号、名称、联系人、电话、地址、状态、备注。
- 原材料：编号、名称、类别、规格、颜色、单位、默认供应商（可选）、状态。
- 服装产品：产品编号、名称、品类、款式、季节/系列（可选）、描述、状态。
- SKU：SKU 编码、所属产品、颜色、尺码、单位、状态。
- 仓库：仓库编码、名称、位置、状态。

规则：
- 编号必须唯一。
- 被业务记录引用的档案不能直接物理删除，可停用。
- SKU 必须关联一个产品。
- 原材料档案是物料主数据，原材料批次是一次具体到货/检验形成的业务批次，两者不能混为一张表。

## 模块二：采购与来料质检（机器视觉核心模块）

### 5.3 采购订单

页面字段建议：
- 采购订单号（系统生成）
- 供应商
- 下单日期、预计到货日期
- 订单明细：原材料、规格、数量、单位、单价（可选）、备注
- 订单状态、创建人、提交时间

订单状态：
- `DRAFT` 草稿
- `SUBMITTED` 已提交
- `PARTIAL_RECEIVED` 部分到货
- `COMPLETED` 已完成
- `CANCELLED` 已取消

规则：
- 草稿可编辑；提交后不允许随意修改关键明细，确需修改应有明确规则或作废重建。
- 订单可以分批到货。
- 已到货数量不能超过订单数量，除非业务规则明确允许超收。
- 订单全部到货后更新为已完成；部分到货则为部分到货。

### 5.4 到货登记与原材料批次

到货登记字段：
- 采购订单号、供应商、到货日期、到货数量、供应商批次号、到货备注。
- 一次到货可以形成一个或多个原材料批次；第一版可以约定“一条到货明细对应一个原材料批次”，降低复杂度。

原材料批次字段：
- 系统批次号（唯一）
- 原材料 ID
- 供应商 ID
- 来源采购订单/采购明细
- 供应商批次号（可空）
- 到货数量、单位、到货日期
- 检验状态、入库状态、可用数量
- 创建人、创建时间

原材料批次状态建议：
- `PENDING_INSPECTION` 待检
- `INSPECTING` 检测中
- `PENDING_REVIEW` 待人工复核
- `QUALIFIED` 检验合格
- `UNQUALIFIED` 检验不合格
- `STOCKED` 已入库
- `DEPLETED` 已耗尽
- `ON_HOLD` 暂停使用/待处理

关键规则：
- 到货登记不代表原材料可以直接投入生产。
- 新批次先处于待检状态。
- 只有正式质检结论合格后，才允许进入可用库存。
- 不合格批次只能按业务规则退货、隔离或报废，不允许正常领料。
- 如果批次已被领料/入库/追溯引用，不能直接删除。

### 5.5 机器视觉检测页面（只检测布料来料图片）

页面流程：
1. 用户先选择一个原材料批次。
2. 页面展示批次号、原材料名称、供应商、采购订单、到货数量、当前检验状态等只读信息。
3. 用户上传布料图片，可一次上传多张，但第一版可先实现单张图片。
4. 前端校验文件类型和大小；后端再次校验。
5. 用户点击“开始检测”，Spring Boot 将图片及批次关联信息提交给 Python YOLO 服务。
6. YOLO 服务返回缺陷类别、置信度、位置框、标注图路径等结构化结果。
7. 页面展示原图/标注图、检测结果表、缺陷数量和检测时间。
8. 检测结果进入“待人工复核”，由质检人员查看图片与结果，填写复核意见和正式质检结论。
9. 保存后更新原材料批次检验状态，并写入操作日志。

**重要：系统不会通过布料图片自动判断图片来自哪个供应商或哪个批次。** 必须先由用户选择已有原材料批次，再上传图片。图片、YOLO 结果和质检记录都关联该批次。这既符合实际业务，也避免错误地根据图像猜测来源。

### 5.6 YOLO 接入约定

Spring Boot 负责业务流程和权限；Python 服务只负责图像推理。建议接口：

`POST /api/v1/detect`

请求使用 multipart/form-data：
- `file`：布料图片。
- 可选 `request_id`：调用请求标识。
- 业务批次关联仍以 Spring Boot 中保存的记录为准；Python 服务不直接操作业务数据库。

成功返回示例：

```json
{
  "success": true,
  "model_name": "fabric-defect-yolo",
  "model_version": "v1",
  "image_width": 1920,
  "image_height": 1080,
  "detections": [
    {
      "class_id": 0,
      "class_name": "hole",
      "confidence": 0.91,
      "bbox": [120, 85, 240, 190]
    }
  ],
  "annotated_image_path": "/vision-results/example.jpg",
  "inference_time_ms": 138
}
```

字段和缺陷类别必须以实际模型输出为准。上面只是接口格式示例，不代表当前已经有模型权重或这些类别可被真实识别。

Python 服务至少应：
- 提供健康检查接口，例如 `GET /health`。
- 校验文件格式、图片能否正常读取。
- 统一返回 JSON；失败时给出明确错误码/错误信息。
- 模型路径从配置读取，不要硬编码绝对路径。
- 返回置信度、类别和坐标；若有标注图则返回路径。
- 不要把“没有检测框”自动解释为“质检合格”，因为模型可能漏检或未正确加载。
- 如果当前没有可用权重，先定义清晰的服务接口并在开发环境标记“检测服务未配置/演示模式”，不能把随机结果伪装成真实检测结果。后续接入权重时替换推理实现。

### 5.7 检测结果与质检结论必须分开

建议分为两类记录：

**机器视觉检测记录**：原图、标注图、模型名称/版本、检测类别、置信度、位置框、推理时间、调用状态、检测人、检测时间。

**人工质检记录**：复核人、复核时间、复核意见、正式结论（合格/不合格/待处理）、处理方式、备注。

机器视觉结果是辅助证据，不能直接覆盖正式质检结论。一个批次可存在多次检测/复核记录，需保留历史。

## 模块三：生产与质量管理

### 5.8 生产计划与工单

生产计划字段：
- 计划编号、产品/SKU、计划数量、计划开始/结束日期、优先级、计划状态、备注。

工单字段：
- 工单编号、关联生产计划、产品/SKU、计划生产数量、已完成数量、负责人、开始日期、预计完成日期、工单状态。

工单状态建议：
- `PENDING` 待执行
- `IN_PROGRESS` 生产中
- `PENDING_QC` 待成品质检
- `REWORKING` 返工中
- `COMPLETED` 已完成
- `CANCELLED` 已取消

第一版只做人工创建/登记的基础生产计划和工单，不做复杂自动排产算法。

### 5.9 领料与原材料追踪

领料记录至少包含：
- 领料单号、工单号、领料人、领料时间、审核/处理状态。
- 领料明细：原材料批次、领料数量、单位、备注。

规则：
- 每条领料明细必须关联具体原材料批次，不能只记录原材料名称。
- 只能从已质检合格、可用库存充足的批次领料。
- 领料成功时通过后端事务生成库存出库流水，并扣减对应批次可用库存。
- 领料记录是原材料批次追溯到生产工单的关键关系。
- 一张工单可使用多个原材料批次；同一个原材料批次也可能被多个工单使用。

### 5.10 生产进度

记录字段：
- 工单号、工序/进度说明、完成数量、进度百分比（可计算）、登记人、登记时间、备注。
- 第一版可使用简化的进度记录，不要求建立复杂工序引擎。
- 已完成数量不得无理由超过计划数量；发生报废或返工时应有相应记录。

### 5.11 成品质检与不合格处理

成品质检由人员人工录入，不要求调用 YOLO 检测成品。字段：
- 工单号、产品/SKU、待检数量、合格数量、不合格数量、检验人、检验时间、检验结果、备注。
- 检验结果：待检、合格、不合格、返工、待复检、报废等。

不合格处理：
- 返工：生成/记录返工任务，完成后进入复检。
- 复检：记录复检人、时间、结果。
- 报废：记录报废数量、原因、操作人和时间。
- 所有数量需校验，合格数量 + 不合格数量不能大于本次送检数量；若有拆分/多次检验，应明确每次检验的数量边界。

规则：
- 只有成品质检合格的数量才能转入可售成品库存。
- 返工品不能直接入可售库存，必须复检通过。
- 成品质检记录要关联工单，并在后续生成成品批次时建立关联。

---

## 模块四：仓储与库存管理

### 5.12 库存管理

管理原材料库存和成品库存，支持：
- 库存查询：按仓库、物料/产品、SKU、批次、库存状态筛选。
- 入库登记。
- 出库登记。
- 库存流水查询。
- 批次库存明细。

库存设计建议同时保存：
1. **库存余额**：便于快速查询。
2. **库存流水**：记录每次入库、出库、调整的业务原因和来源。

流水字段建议：
- 流水号、仓库、库存对象类型、原材料/产品/SKU、批次号、业务类型、入/出库数量、变更前数量、变更后数量、关联业务单号、操作人、操作时间、备注。

业务类型示例：
- 原材料合格入库
- 生产领料出库
- 成品合格入库
- 销售发货出库
- 退货待验收
- 库存盘点调整（第一版可选）

### 5.13 库存业务规则

- 到货登记本身不直接增加可用库存；通过质检合格后再执行原材料入库。
- 库存数量不能为负。
- 库存更新和流水创建必须放在同一数据库事务中。
- 出库时要锁定或校验库存，防止并发导致超卖/负库存。
- 不允许用户在普通页面直接编辑库存余额；调整必须产生流水和原因。
- 成品入库必须校验对应批次/数量已通过成品质检。
- 销售发货必须关联具体成品批次，并产生销售出库流水。
- 退货产品先进入待验收/隔离状态；通过验收后才能决定是否恢复可售库存。

### 5.14 成品批次

成品批次字段：
- 成品批次号、工单号、产品/SKU、生产数量、质检合格数量、入库数量、当前状态、生产日期、仓库。
- 一个工单可以产生多个成品批次。
- 成品批次应关联对应工单和成品质检记录。
- 如果一个工单使用多个原材料批次，应通过领料明细/用料关联表建立多对多追溯关系，不要只在成品批次里存一个原材料批次 ID。

---

## 模块五：销售与售后管理

### 5.15 销售订单

字段：
- 销售订单号、客户名称/编号（第一版可用简单客户档案或文本字段）、下单日期、订单明细、数量、备注、状态。

订单状态：
- `DRAFT` 草稿
- `PENDING_SHIPMENT` 待发货
- `PARTIAL_SHIPPED` 部分发货
- `SHIPPED` 已发货
- `COMPLETED` 已完成
- `CANCELLED` 已取消

规则：
- 订单可分批发货。
- 已发货数量不能超过订单数量。
- 取消订单不能删除已经产生的发货/出库历史。

### 5.16 发货

发货单字段：
- 发货单号、销售订单号、发货日期、物流单号（可选）、经办人、状态、备注。
- 发货明细：成品批次、SKU、发货数量。

规则：
- 发货必须选择通过成品质检且处于可售库存状态的成品批次。
- 发货数量不能超过订单剩余待发数量或对应批次可用库存。
- 发货确认时，在同一事务内扣减库存、创建库存流水、保存发货明细并更新销售订单状态。
- 一张销售订单可以多次发货；一个成品批次也可能分多次发给不同订单。

### 5.17 售后处理

字段：
- 售后单号、关联销售订单、关联发货单/成品批次（尽量关联到批次）、售后类型（退货/换货/维修/咨询等）、问题描述、申请日期、处理状态、处理结论、验收结果、经办人、备注。

规则：
- 退货不直接增加可售库存。
- 退回商品先记录退货到货和待验收状态；根据验收结果决定恢复可售、维修/返工、报废或其他处理。
- 售后记录必须能关联到原销售订单和尽可能具体的成品批次，以支持反向追溯。

## 模块六：生命周期追溯与统计分析

### 5.18 追溯页面

提供两种主要查询：

**正向追溯：从原材料批次出发**
- 供应商 → 采购订单/采购明细 → 到货登记 → 原材料批次
- 原材料批次 → 图片检测记录 → 人工质检结论
- 原材料批次 → 领料记录 → 生产工单/生产进度
- 生产工单 → 成品批次 → 成品质检
- 成品批次 → 库存流水 → 销售订单/发货单 → 售后记录

**反向追溯：从成品/售后出发**
- 售后单/销售订单/成品批次
- 查到对应发货明细和成品批次
- 查到生产工单、成品质检、生产进度
- 查到领料明细及所有关联原材料批次
- 查到原材料供应商、采购订单、来料检测和质检结论

展示方式：
- 顶部显示查询对象的编号、名称、状态和关键日期。
- 主体使用时间线、步骤卡片或树状关联表格展示业务链。
- 每个节点可点击查看详情。
- 缺失某类记录时显示“暂无记录”，不应把空值伪装成完整链路。
- 追溯结果由数据库关联关系查询得到，不依赖 AI 生成。

### 5.19 统计分析

第一版只实现简单且可解释的统计：
- 采购订单数量、到货数量、待检批次数。
- 来料检测批次数、缺陷数量/类别分布、合格率（统计口径必须说明）。
- 工单数量、生产完成数量、返工/报废数量。
- 原材料/成品库存数量和库存预警（可选）。
- 销售订单数、发货数量、售后单数量。

统计数据必须来自实际业务表，不要写死假数据。图表可以使用 ECharts；如果时间不足，使用数字卡片 + 简单表格也可以。

## 6. 核心业务流程与状态流转

### 6.1 完整业务链

```text
基础档案
  ↓
采购订单
  ↓
到货登记
  ↓
原材料批次（待检）
  ↓
上传布料图片 → YOLO 检测 → 检测结果待人工复核
  ↓
人工复核并保存正式质检结论
  ├─ 不合格 → 隔离/退货/报废等处理，不进入可用库存
  └─ 合格 → 原材料入库 → 可用库存
                    ↓
              生产计划/工单
                    ↓
              关联原材料批次领料
                    ↓
                 生产进度
                    ↓
                 成品质检
              ├─ 不合格 → 返工/复检/报废
              └─ 合格 → 创建成品批次 → 成品入库
                                      ↓
                                  销售订单
                                      ↓
                              选择成品批次发货
                                      ↓
                                  售后处理
                                      ↓
                              生命周期正反向追溯
```

### 6.2 状态不能随意跳转

建议将状态变更封装在 Service 层，不能由前端直接提交任意状态值。举例：
- 原材料批次：待检 → 待复核 → 合格/不合格；合格后才允许入库。
- 工单：待执行 → 生产中 → 待成品质检 → 完成；返工时进入返工流程。
- 成品批次：待质检/待入库 → 合格可入库 → 可售库存；未通过质检不能进入可售库存。
- 销售订单：草稿 → 待发货 → 部分发货/已发货 → 完成。
- 售后：待处理 → 处理中 → 待验收 → 完成/关闭。

实际状态可以根据实现合并，但每次变更必须有合法前置条件，并保存必要的操作人、时间和原因。

## 7. 数据库设计建议

以下为逻辑设计清单，不要求第一版严格一表不差。可根据实际复杂度合并部分表，但不能丢失关键追溯关系、权限控制和库存流水。所有业务表建议包含 `id`、创建时间、更新时间；重要记录增加创建人/更新人、状态和业务编号。

### 7.1 系统与基础数据

- `sys_user`：用户账号、密码哈希、姓名、状态等。
- `sys_role`：角色编码、角色名称、说明。
- `sys_permission`：菜单/按钮权限编码、名称、类型。
- `sys_user_role`：用户与角色关联。
- `sys_role_permission`：角色与权限关联。
- `sys_operation_log`：操作人、动作、对象类型/ID、摘要、时间、结果。
- `supplier`：供应商资料。
- `material`：原材料主数据。
- `product`：服装产品主数据。
- `product_sku`：产品 SKU。
- `warehouse`：仓库资料。

### 7.2 采购与质检

- `purchase_order`：采购订单主表。
- `purchase_order_item`：采购订单明细。
- `arrival_record`：到货登记主表（第一版可视业务需要简化）。
- `material_batch`：原材料批次及其采购来源、质检/入库状态。
- `inspection_record`：人工质检/复核主记录。
- `inspection_image`：上传原图、图片路径、批次关联、上传人等。
- `vision_detection_result`：模型、版本、调用状态、推理时间、检测结果 JSON、标注图路径等。

建议把一张图中的多个检测框保存在 JSON 字段或独立的 `vision_detection_item` 表中。若要按缺陷类别做可靠统计，独立明细表更合适；若时间紧，可先存 JSON，但统计功能需要相应处理。

### 7.3 生产与质量

- `production_plan`：生产计划。
- `work_order`：生产工单。
- `material_issue`：领料单主表。
- `material_issue_item`：领料明细，必须关联 `material_batch_id`。
- `production_progress`：进度登记。
- `finished_inspection`：成品质检记录。
- `quality_disposition`：返工、复检、报废等处理记录。
- `finished_batch`：成品批次，关联工单和产品/SKU。
- `finished_batch_material`：成品批次与原材料批次关联；若第一版已经通过工单领料明细和工单关系可以准确推导，也仍建议保留清晰的追溯查询逻辑，避免错误地把一个成品批次只关联单一原料批次。

### 7.4 库存、销售与售后

- `inventory`：库存余额，按仓库 + 库存对象类型 + 批次等唯一维度保存。
- `inventory_transaction`：库存流水，记录业务来源、入/出数量、前后余额。
- `sales_order`：销售订单。
- `sales_order_item`：销售订单明细。
- `shipment`：发货单主表。
- `shipment_item`：发货明细，必须关联成品批次。
- `after_sales_record`：售后记录，关联订单/发货/成品批次。

### 7.5 关键关系与约束

- 一个供应商可关联多个采购订单。
- 一个采购订单有多条采购明细；一个采购明细可以分多次到货。
- 一个原材料批次对应一个原材料，且应能查到来源采购订单/明细。
- 一个原材料批次可产生多次图片检测和复核记录。
- 一个工单可领用多个原材料批次；一个原材料批次也可被多个工单使用，使用 `material_issue_item` 表示多对多关系。
- 一个工单可产生多个成品批次。
- 一个成品批次可分多次发货，也可出现在不同发货单明细中。
- 所有库存变化都必须有库存流水。
- 业务编号唯一；重要数量必须非负；外键或等价应用层约束要保证关联数据有效。
- 业务历史原则上采用逻辑删除/作废，不物理删除已被引用的关键记录。

## 9. 统一编码约定

### 9.1 后端

- Controller 只负责接收请求、基础参数校验、调用 Service、返回结果。
- 业务规则写在 Service 层，不要堆在 Controller 中。
- 库存更新、领料、发货、合格入库等涉及多表的数据变更必须使用事务。
- DTO 用于接收输入，VO 用于返回页面所需字段；不要直接把数据库实体当作所有接口的输入输出对象。
- 统一异常处理、统一分页结构、统一响应格式。
- 所有写操作进行后端权限校验。
- 关键状态变更校验当前状态和前置条件。
- 对库存数量、订单数量、质检数量进行服务端校验，不能只靠前端。
- 不在代码中硬编码数据库密码、API 密钥、模型绝对路径。
- 日志不输出密码、令牌或其他敏感信息。

### 9.2 前端

- 按业务模块组织 API 文件和页面组件。
- Axios 统一处理 baseURL、认证信息、错误提示和超时。
- 登录后获取当前用户、角色和权限，再构建菜单。
- 路由守卫控制页面访问；后端仍需独立鉴权。
- 表格列表统一使用分页、查询、重置、空状态、加载状态。
- 所有提交按钮在请求中显示 loading，避免重复提交。
- 图片上传页面显示上传进度/失败信息，限制格式和大小。
- 不把权限判断、库存规则或业务状态的最终决定只放在前端。

### 9.3 Python 服务

- 使用固定依赖版本并记录在 `requirements.txt`。
- 模型初始化失败时应明确报错，不得返回伪造检测结果。
- 推理接口需要限制文件类型/尺寸，处理损坏图片和超时。
- 输出 JSON 字段稳定，并记录模型版本。
- 业务批次关联由 Spring Boot 保存；Python 服务不直接决定质检合格/不合格。

## 10. 建议开发顺序（必须小步迭代）

不要要求 Claude Code 一次性生成整个系统。每一阶段都要能运行、可测试，再进入下一阶段。

### 阶段 0：检查环境与建立项目骨架
1. 检查现有仓库、Node/Java/Python 版本、依赖和启动方式。
2. 先输出当前项目结构和实施计划，不要未经确认删除或重建已有文件。
3. 建立前后端和 Python 服务骨架。
4. 配置数据库连接、统一响应、异常处理、日志和 README。
5. 提供 `.env.example`，不提交真实密码或密钥。
6. 验收：前端、后端、Python 健康检查能分别启动。

### 阶段 1：登录、权限和统一布局
1. 完成登录、退出、当前用户信息。
2. 完成四种角色和基础权限数据。
3. 完成统一后台布局、动态菜单、路由守卫。
4. 完成用户/角色管理和操作日志基础功能。
5. 验收：四类角色登录后菜单不同；未授权后端接口返回 401/403，而不是仅隐藏按钮。

### 阶段 2：基础档案
1. 供应商、原材料、产品、SKU、仓库的增删改查。
2. 统一分页、筛选、状态标签和表单校验。
3. 编号唯一、引用数据不能物理删除。
4. 验收：能创建一套可用于后续流程的基础数据。

### 阶段 3：采购、到货、批次和来料质检
1. 采购订单主表/明细、提交和状态变化。
2. 到货登记、创建原材料批次。
3. 批次详情页及状态展示。
4. 上传布料图片并保存图片元数据。
5. 建立 YOLO Python 接口，完成真实模型接入或明确的“未配置”状态。
6. 保存检测结果、人工复核记录和正式质检结论。
7. 验收：可以从采购订单追到原材料批次、图片检测结果和人工复核结果；不合格批次无法正常入库/领料。

### 阶段 4：生产与成品质检
1. 生产计划、工单。
2. 领料单及领料明细，关联原材料批次。
3. 领料扣减库存并生成流水（可在阶段 5 建好库存后再完成联调）。
4. 生产进度登记。
5. 成品质检、返工、复检、报废。
6. 创建成品批次并关联工单。
7. 验收：能够从工单查询所有领用的原材料批次；不合格成品无法正常入库。

### 阶段 5：库存、销售和售后
1. 库存余额、库存流水。
2. 原材料合格入库、生产领料出库、成品合格入库。
3. 销售订单、发货单、发货明细。
4. 发货事务扣减库存并生成流水。
5. 售后记录、退货验收和处理状态。
6. 验收：库存数量与流水一致；负库存被阻止；发货关联具体成品批次；退货不自动恢复可售库存。

### 阶段 6：追溯与统计
1. 原材料批次正向追溯。
2. 成品批次和售后记录反向追溯。
3. 工作台统计卡片和基础统计页面。
4. 验收：至少用一套完整的测试数据演示“采购→来料质检→生产→成品质检→入库→销售发货→售后”的追溯闭环。

### 阶段 7：系统测试、部署和文档
1. 测试主要成功路径、失败路径、越权访问、库存边界和状态流转。
2. 准备演示数据和测试账号。
3. 编写部署说明、运行说明、用户操作说明。
4. 整理数据库初始化脚本、接口文档、系统截图。
5. 验收：其他人按 README 可以启动系统并完成核心演示流程。

## 11. 必须覆盖的测试场景

- 未登录访问受保护接口应失败。
- 采购人员不能调用质检复核、库存出库等未授权接口。
- 待检/不合格原材料批次不能正常领料。
- YOLO 服务不可用、图片损坏或格式不支持时，系统给出清楚提示且不伪造结果。
- YOLO 没有检测框不等于自动质检合格。
- 质检复核提交后保留检测历史和复核人信息。
- 成品质检不合格时，不能进入可售库存。
- 库存不足时领料/发货失败，库存余额和流水都不能发生部分更新。
- 同一发货请求重复提交时，应尽量避免重复扣库存（可用幂等校验或状态校验）。
- 退货未验收前不增加可售库存。
- 追溯时能展示所有关联原材料批次，不只展示一个。
- 被引用的供应商、批次、工单、发货单不能被直接物理删除。
- 分页、筛选、空数据、网络失败和服务端错误都有正常 UI 状态。

## 13. 给 Claude Code 的执行指令

以下规则建议在每次开发任务开始时遵守：

1. **先读文档和仓库**：先阅读 `docs/SYSTEM_DESIGN.md`、`README.md`、现有目录和相关代码，再动手。
2. **先计划再修改**：先列出本次要改的文件、数据库变化、接口、页面和测试，再按步骤执行。
3. **一次聚焦一个小模块**：不要一次性生成所有模块。每次完成一个闭环，例如“原材料档案 CRUD”，再运行和测试。
4. **不随意推翻技术选型**：沿用 Vue 3 + Element Plus、Spring Boot、MySQL、Python YOLO；如果项目已经采用可兼容的等价方案，先说明再沿用。
5. **不伪造 AI 功能**：没有模型权重就明确提示未配置；不要随机生成缺陷框或假装模型已检测。
6. **业务规则在后端实现**：前端隐藏按钮不等于安全；库存和状态变更必须由后端校验。
7. **保留追溯关系**：每次新增/修改采购、批次、领料、成品、发货、售后功能时，检查追溯链是否完整。
8. **数据库改动可追踪**：更新 `schema.sql` 或迁移脚本，并提供必要的初始化/升级说明；不要只改实体类不改数据库。
9. **运行测试并报告**：每次完成后说明修改文件、实现内容、启动命令、测试结果、未完成项和下一步。若测试没运行或失败，明确写出原因，不要声称通过。
10. **保护已有数据和文件**：除非用户明确同意，不要删除现有数据库、清空数据、覆盖用户文件或重写整个项目。
11. **不引入不必要依赖**：优先使用已有依赖；新增依赖前说明用途。
12. **遇到设计冲突先说明**：如果代码现状、论文要求与本文冲突，列出冲突和建议，不要自行扩大范围。

## 14. 最终验收标准

系统至少满足以下条件，才算核心目标完成：

- 四类角色能登录，并根据权限访问对应模块。
- 供应商、原材料、产品、SKU 等基础数据可以维护。
- 能创建采购订单、登记到货并形成原材料批次。
- 能在指定原材料批次下上传布料图片，保存检测结果并由人员复核。
- 能记录生产计划、工单、领料批次、生产进度和成品质检。
- 能对合格原材料、合格成品进行入库，并对领料/发货执行出库。
- 库存余额和库存流水保持一致，阻止负库存和非法状态跳转。
- 能记录销售订单、发货和售后。
- 能从原材料批次正向查到生产、成品、销售与售后，也能从成品/售后反向查到原材料来源。
- 系统有可运行说明、数据库脚本、核心测试和演示数据。
- 机器视觉能力按实际模型接入情况如实呈现，不虚构检测效果。

**开发优先级总结：先把业务链、权限、库存一致性和追溯关系做正确；再完善视觉检测接入；最后做统计、美化和非核心功能。**
